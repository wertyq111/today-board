# 天气看门板 PRD

## 1. 产品结论

| 项目 | 结论 |
| --- | --- |
| 产品名 | 天气看门板 |
| 产品定位 | 一个完全本地运行的晨间看板 App，专注天气提醒、日程感知和出门清单 |
| 目标用户 | 有固定上班或出门节奏、但不想维护复杂效率工具的人 |
| 核心场景 | 起床后到出门前 15 分钟内，快速确认今天要带什么、注意什么 |
| 第一版边界 | 不做后端、不做地图、不做路线、不做账号同步、不做复杂推送 |
| 核心价值 | 把“天气 + 今天最重要的日程 + 出门清单”压缩成一眼能看懂的晨间看板 |

## 2. 为什么这条路可行

### 2.1 可行结论

这条产品线是可行的，而且比现在“天气 + 地图 + 出行方案”的组合更稳。

当前项目本来就是 `local-only HarmonyOS app`，清单、本地规则、日历读取、服务卡片都已经是本地链路。真正不稳的是两个点：

1. 地图地点搜索依赖高德 Web 服务 Key，长期放在 App 端不现实。
2. 当前真实天气依赖系统天气能力，而我们已经验证过当前设备缺少对应运行组件，现有 [WeatherService.ets](/Volumes/AgentAPFS/Program/Personal/today-board/entry/src/main/ets/services/WeatherService.ets:1) 会直接返回 `unavailable`。

所以结论不是“无后端就不能做”，而是：

- 无后端 + 无地图：能做，而且更稳。
- 无后端 + 稳定真实天气：不能把它当第一版的强依赖。

### 2.2 天气能力策略

| 层级 | 是否进入第一版 | 说明 |
| --- | --- | --- |
| 系统天气能力 | 是，作为增强项 | 设备支持就接入；不支持就直接显示未接入 |
| 第三方天气 API 直连 | 否 | 本质仍会暴露第三方 Key，不符合这次收缩方向 |
| 手动天气标签 | 是 | 用户主动选择“晴 / 雨 / 降温 / 大风”，不是假数据，是显式输入 |

第一版推荐策略：

1. 默认尝试系统天气能力。
2. 拿不到时，不静默猜测，不接第三方 Key。
3. 让用户在首页或设置页显式切换手动天气标签。

这样产品不会因为天气能力失败而不可用。

## 3. 用户问题与产品目标

### 3.1 要解决的问题

| 问题 | 现在的痛点 |
| --- | --- |
| 天气知道得太晚 | 出门后才发现下雨、降温、闷热 |
| 清单总是靠记忆 | 工牌、雨伞、水杯、耳机容易漏 |
| 日程和天气是分散的 | 日历知道今天有会，天气知道会下雨，但没人把它们串起来 |
| 现在的产品主线太重 | 地图、路线、地点搜索把体验拉得太复杂 |

### 3.2 产品目标

| 目标 | 标准 |
| --- | --- |
| 30 秒看懂今天 | 首页首屏必须在 30 秒内读完 |
| 少做判断，多给结论 | 不做信息堆叠，只给今天最值得注意的 1-3 件事 |
| 没天气也能用 | 天气不可用时，日程和清单仍完整可用 |
| 无后端可上线 | 第一版不依赖任何自建服务 |

## 4. MVP 功能范围

| 模块 | 第一版是否进入 | 说明 |
| --- | --- | --- |
| 首页看板 | 是 | 天气结论、今日提醒、日程预览、清单预览 |
| 出门清单 | 是 | 支持模板、勾选、天气触发附加项 |
| 提醒规则页 | 是 | 配置天气规则、时间规则、日程规则 |
| 设置页 | 是 | 权限、天气来源、主题、静默时段 |
| 桌面服务卡片 | 是 | 展示今日提醒和必带项 |
| 地图搜索 | 否 | 整体移除 |
| 出行方案决策 | 否 | 整体移除 |
| 账号同步 | 否 | 第一版不上 |
| 后台推送 | 否 | 第一版不上 |

### 5.1 页面结构

| 页面 | 作用 | 关键内容 |
| --- | --- | --- |
| 看板 | 晨间总览 | 天气状态、提醒结论、最近日程、必带清单 |
| 清单 | 管理要带的东西 | 必带项、已带状态、模板、天气附加项 |
| 提醒 | 管理规则 | 天气规则、日程规则、时间规则、命中历史 |

| Tab | 名称 | 说明 |
| --- | --- | --- |
| 1 | 看板 | 首页主入口 |

| 3 | 提醒 | 规则和命中 |
| 4 | 我的 | 权限和个性设置 |

## 6. 数据来源与本地规则

### 6.1 数据来源

| 数据 | 来源 | 是否强依赖 |
| --- | --- | --- |
| 当前日期时间 | 系统时间 | 是 |
| 今日日程 | 系统日历权限 | 否 |
| 出门清单 | 本地存储 | 是 |
| 天气 | 系统天气能力 | 否 |
| 手动天气标签 | 用户本地输入 | 否，但建议有 |

### 6.2 规则引擎

| 规则类型 | 示例 | 输出 |
| --- | --- | --- |
| 天气规则 | 下雨 -> 加入雨伞 | 首页提醒 + 清单附加项 |
| 温度规则 | 大于 26°C -> 加入水杯 | 首页提醒 + 清单附加项 |
| 日程规则 | 标题含“会” -> 加入耳机 | 首页提醒 |
| 时间规则 | 早上 6:30 - 9:30 才显示完整看板 | 首页模式切换 |

### 6.3 首页结论生成规则

首页不再输出“路线推荐”，改为输出“晨间提醒结论”。

输出结构固定为三段：

1. 今天最重要的提醒一句话。
2. 为什么要提醒。
3. 现在需要检查的 1-3 项。

例如：

- 今天带伞，10:20 后会下雨。
- 今天薄外套可不带，但水杯别省。
- 上午两场会，工牌和耳机放最前面。

## 7. 交互设计标准

### 7.1 首页标准

| 规则 | 标准 |
| --- | --- |
| 首屏重点 | 只允许一个主结论，不能再堆多个主 CTA |
| 信息分层 | 大标题 > 原因文案 > 数值块 > 提醒块 |
| 天气不可用 | 明确显示“系统天气未接入”或“手动天气模式” |
| 清单预览 | 只展示 4 个最重要物品，更多内容进清单页 |

### 7.2 视觉标准

| 项目 | 标准 |
| --- | --- |
| 视觉隐喻 | 天空毛玻璃晨间看板 |
| 色彩 | 浅蓝、白、橙、绿色，强调“清晨和提醒” |
| 卡片 | 半透明玻璃卡，强圆角，弱描边 |
| 图标 | 统一使用现有 `tb_icon_*` 资源，全部按固定槽位布局 |
| 底部导航 | 固定底部，4 个入口，不再沿用“出行 / 发现”语义 |

## 8. 技术方案

### 8.1 保留

| 模块 | 处理方式 |
| --- | --- |
| 本地存储 | 保留 |
| 日历权限与读取 | 保留 |
| 服务卡片 | 保留，但内容改成天气提醒和清单 |
| 当前主题资源 | 保留并继续扩展 |

### 8.2 移除或降级

| 模块 | 处理方式 |
| --- | --- |
| 地图搜索 | 整体移除 |
| 高德 Key 配置 | 整体移除 |
| 出行决策引擎 | 移除主链路，不再作为首页核心 |
| 通勤方案页 | 改造成“提醒规则页” |

### 8.3 天气模块实现建议

| 方案 | 建议 |
| --- | --- |
| 继续保留系统天气接口 | 是，但只能算可选增强 |
| 在 App 端接第三方天气 API | 不建议 |
| 手动天气标签 | 必须加入 |

## 9. 验收标准

| 验收项 | 标准 |
| --- | --- |
| 无后端可运行 | 断网情况下仍可进入看板、清单、提醒、我的 |
| 无天气可运行 | 系统天气失败时仍能完整使用清单和日程功能 |
| 晨间信息清晰 | 首页 30 秒内能读完主结论 |
| 规则透明 | 每条提醒都能解释“为什么出现” |
| 不再依赖第三方地图 Key | 设置页不再有地图配置入口 |

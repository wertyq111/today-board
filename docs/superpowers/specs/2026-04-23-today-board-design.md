# 今日出门板设计文档

## 1. 产品定义

| 项目 | 设计 |
| --- | --- |
| 产品名 | 今日出门板 |
| 一句话 | 早晨打开一次，立刻知道今天几点走、穿什么、带什么、选哪种通勤方式 |
| 目标用户 | 上班通勤人群 |
| 核心场景 | 起床后到出门前这 30 分钟 |
| 产品边界 | 不做登录、不做社交、不做后端、不做远端部署、不做真实导航闭环、不做复杂地图页 |
| 第一版亮点 | 首页晨报结论 + 混合通勤决策 + 桌面服务卡片 |

## 2. 设计结论

| 维度 | 结论 |
| --- | --- |
| 首页结构 | 头图总览 + 时间轴式信息分层 |
| 视觉方向 | 天气玻璃卡，轻盈干净，偏晨间系统感 |
| 服务卡片 | 单结论卡，只给最关键结果 |
| 核心决策 | 直接推荐今天更适合的通勤方案 |
| 数据来源 | 定位、天气、系统日历、用户本地配置 |
| 技术方向 | Stage + ArkTS + ArkUI |

## 3. MVP 功能范围

| 模块 | 第一版是否进入 | 说明 |
| --- | --- | --- |
| 今日总览头图 | 是 | 显示天气、体感、降雨提醒和一句结论 |
| 通勤决策卡 | 是 | 直接告诉用户今天更适合哪种通勤方式，以及为什么 |
| 今日日程卡 | 是 | 读取系统日历，只显示最近 1 到 3 条 |
| 出门清单卡 | 是 | 提醒雨伞、水杯、工牌等，可手动勾选 |
| 天气趋势卡 | 是 | 告诉用户几点变热、几点可能下雨 |
| 桌面服务卡片 | 是 | 在桌面直接展示怎么走、几点走、是否带伞 |
| 独立地图页 | 否 | 太重，第一版不做 |
| 复杂路线比价 | 否 | 不接真实路线引擎 |
| 账号同步 | 否 | 第一版不上后端 |

## 4. 页面结构

| 页面 | 作用 | 内容 |
| --- | --- | --- |
| 首次配置页 | 一次性配齐决策输入 | 家、公司、上班时间、常用通勤方案、默认出门清单 |
| 首页 | 早晨 30 秒看懂今天 | 今日结论头图、通勤决策卡、最近日程、出门清单、天气趋势 |
| 通勤方案配置页 | 修改用户规则 | 地铁、打车、公交+步行等方案名称、耗时、费用、雨天影响、偏好权重 |
| 出门清单配置页 | 让提醒更贴近个人习惯 | 工牌、耳机、水杯、雨伞、充电器等 |
| 设置页 | 放权限和基础配置 | 定位权限、日历权限、公司地址、刷新时间 |
| 桌面服务卡片 | 抬手看结果 | 单结论：今天更适合怎么走 + 几点前出门 + 是否带伞 |

## 5. 核心决策规则

### 5.1 输入

| 输入 | 作用 |
| --- | --- |
| 当前时间 | 判断离出门还有多久 |
| 当天第一条日程开始时间 | 计算最晚出发时刻 |
| 天气与降雨时间 | 判断是否要避雨、是否要提前出门 |
| 用户配置的通勤方案 | 提供每种方案的耗时、成本、舒适度和雨天影响 |
| 当前定位 | 判断是否处于早晨出门场景 |

### 5.2 输出

| 输出 | 说明 |
| --- | --- |
| 推荐方案 | 地铁 / 打车 / 公交+步行等三选一 |
| 推荐出门时间 | 日程开始时间 - 方案耗时 - 缓冲时间 |
| 随身提醒 | 带伞、带外套、带水杯等 |
| 风险提示 | 例如再晚 10 分钟出门就更适合打车 |

### 5.3 规则原则

| 场景 | 规则 |
| --- | --- |
| 时间快不够了 | 优先更快方案 |
| 临近降雨 | 优先更少暴露在室外的方案 |
| 时间充足且天气好 | 优先更省钱或更稳定方案 |
| 用户明显不常用某方案 | 降低优先级，但不隐藏 |
| 缺少关键数据 | 直接提示无法判断，不偷偷兜底 |

## 6. 信息架构与组件拆分

| 组件 | 职责 | 依赖 |
| --- | --- | --- |
| AppStateStore | 持有全局状态和首页展示数据 | 本地存储、系统能力 |
| SetupFlow | 处理首次配置和权限请求 | 定位、日历、本地存储 |
| CommuteDecisionEngine | 根据透明规则输出推荐结果 | 天气、日历、通勤方案、当前时间 |
| TodayOverviewCard | 展示首页顶部结论 | 决策结果、天气数据 |
| SchedulePreviewCard | 展示最近日程 | 系统日历 |
| PackingChecklistCard | 展示出门清单和勾选状态 | 本地存储、决策结果 |
| WeatherTrendCard | 展示今天天气变化 | 天气数据 |
| ServiceWidgetAdapter | 把首页核心结论压缩成服务卡片内容 | 决策结果、提醒数据 |

## 7. 数据流

| 阶段 | 数据流 |
| --- | --- |
| 首次进入 | 用户完成配置，写入本地存储 |
| 每次打开首页 | 读取本地配置、请求定位、读取系统日历、拉取天气 |
| 生成结论 | 决策引擎计算推荐方案、出门时间、提醒项 |
| 更新页面 | 首页卡片和服务卡片都使用同一份结论数据 |
| 用户调整配置 | 配置页改动后立即重新计算首页结论 |

## 8. 错误处理

| 场景 | 处理方式 |
| --- | --- |
| 没有定位权限 | 明确提示无法生成基于位置的出门建议 |
| 没有日历权限 | 首页保留天气和清单，但通勤结论标记为信息不完整 |
| 天气拉取失败 | 直接显示天气不可用，不使用猜测数据 |
| 通勤方案未配置完成 | 强制回到配置引导，不进入完整首页 |
| 当前定位不在家附近 | 只显示信息晨报，不硬套晨间通勤决策 |

## 9. 测试重点

| 测试项 | 目标 |
| --- | --- |
| 首次配置流程 | 输入完整后能稳定进入首页 |
| 权限拒绝场景 | 定位、日历缺失时明确暴露问题 |
| 决策规则 | 雨天、快迟到、时间充足三类场景下推荐结果正确 |
| 首页信息层级 | 用户 30 秒内能读懂主结论 |
| 服务卡片 | 桌面展示的信息短、准、稳定 |

## 10. 实现约束

| 项目 | 结论 |
| --- | --- |
| 开发模型 | Stage |
| 语言 | ArkTS |
| UI | ArkUI 声明式开发 |
| 存储 | 端上本地存储 |
| 后端 | 第一版不需要 |
| 部署方式 | 本地单端开发与验证 |
| 后台策略 | 不做重后台常驻，以用户主动打开和卡片刷新为主 |
